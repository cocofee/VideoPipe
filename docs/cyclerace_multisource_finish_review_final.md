# CycleRace 多源终点判读系统

## 最终方案与开发计划

**版本：** V1.0
**日期：** 2026-08-20
**适用场景：** 自行车公路赛、绕圈赛、短距离冲刺和集团通过终点的现场判读

## 1. 决策摘要

本方案采用 FinishLynx 的单窗口判读思路，但不复制其代码、内部协议或商业实现。

系统由三部分组成：

```text
CycleRace
  官方芯片计时、通过顺序、正式成绩

VideoPipe
  视频检索、人工判读、证据保存、修正建议

澳亚特软件
  高速线阵相机采集和原始 RGB 文件生成
```

核心边界：

1. CycleRace 是唯一官方成绩来源。
2. VideoPipe 不直接改写 CycleRace 正式成绩。
3. 普通摄像头用于连续视频证据和号码确认。
4. 高速线阵用于精确判断冲线顺序和冲线位置。
5. YOLO、OCR 都不是第一版的必要条件。
6. 原始视频、RGB 和人工观察记录必须保留，不能因识别失败而丢失证据。

## 2. 为什么采用 FinishLynx 式界面

FinishLynx 的可借鉴点是工作流，不是外观：

```text
赛事信息 + 结果表 + 图像判读区 + 普通视频区
```

全部放在同一个比赛事件窗口中。操作员不需要在多个软件之间切换，主要动作被压缩为：

```text
选择通过对象 -> 移动判读位置 -> 查看视频 -> 输入号码 -> Enter 确认
```

对我们的价值：

- 通过记录和视频证据可以联动；
- 线阵图像与普通视频可以使用同一时间轴；
- 结果表不仅显示结果，也是判读导航器；
- 新片段进入待判队列，不打断当前判读；
- 常用操作由工具栏和快捷键完成，复杂配置放入菜单。

## 3. 系统组成和职责

### 3.1 CycleRace

负责：

- 芯片读取；
- 官方通过时间；
- 芯片通过顺序；
- 圈次和比赛状态；
- 正式名次和成绩；
- 人工确认后的正式修正。

发送给 VideoPipe 的数据至少包括：

```text
event_id
passage_id
sequence
chip_id / bib
passage_time_ms
lap
source
```

### 3.2 VideoPipe

负责：

- 接收 CycleRace 通过事件；
- 连续录像和视频时间索引；
- 单摄像头或双摄像头同步回放；
- 澳亚特 RGB 只读适配；
- 人工确认号码和通过顺序；
- 截图、视频片段和原始证据保存；
- 形成修正建议并回传 CycleRace。

当前仓库已经具备多路视频管线基础：RTSP/UDP/文件输入、异步录像、按 `channel_index` 管理多路数据和应用层回调。现有底层还需要补充比赛事件模型、源 PTS 时间索引、统一时间轴和判读界面。

### 3.3 澳亚特软件

负责：

- 控制线阵相机；
- 按现场操作开始和停止拍摄；
- 生成 RGB 原始文件；
- 保持原有采集软件稳定运行。

VideoPipe 通过只读适配器访问 RGB 文件或厂商授权 SDK，不修改澳亚特原始数据。

## 4. 支持的工作模式

| 模式 | 设备 | 主要用途 | 结论 |
|---|---|---|---|
| 基础模式 | CycleRace + 1 台普通摄像头 | 按芯片时间找视频、确认号码、保存证据 | 第一版优先实现 |
| 双摄模式 | CycleRace + 2 台普通摄像头 | 从两个角度确认号码、减少遮挡 | 第二阶段实现 |
| 精确模式 | CycleRace + 澳亚特线阵 | 判断贴身冲线顺序和精确位置 | 线阵适配完成后使用 |
| 完整模式 | CycleRace + 双摄 + 澳亚特 | 芯片、顺序、号码三源互证 | 最终推荐配置 |

### 4.1 基础模式

普通摄像头连续录像，CycleRace 每收到一个芯片通过事件，就在 VideoPipe 的视频时间线上增加标记。操作员点击标记即可跳到目标附近。

这一模式不依赖 YOLO、OCR 或高速相机，可先验证最核心的现场流程。

### 4.2 双摄模式

建议安装：

```text
摄像头 A：终点正面或正侧面，重点看车头和正面号码
摄像头 B：终点反侧面或背面，解决遮挡、重叠和背号不可见
```

两路视频分别保存，不预先拼接。VideoPipe 使用一个主时间线同步控制两路回放，每路保留独立的 `camera_id`、源 PTS 和时间偏移。

### 4.3 精确和完整模式

澳亚特线阵图像负责回答：

```text
谁先通过？
前轮前缘在哪一列？
多个运动员的相对顺序是什么？
```

普通摄像头负责回答：

```text
这个通过对象的号码是多少？
是否能从另一角度确认？
是否存在芯片漏读？
```

CycleRace 仍然负责正式成绩。

## 5. 网络拓扑

使用专用千兆交换机，不要求使用路由器：

```text
CycleRace 电脑 ─┐
VideoPipe 电脑 ─┼── 专用千兆交换机
澳亚特电脑   ──┤
摄像头 A     ──┤
摄像头 B     ──┘
```

如果某台电脑的板载网口已连接设备，增加 USB 千兆网卡：

```text
网口 1：设备连接
网口 2：比赛专网交换机
```

建议：

- 使用固定 IP；
- 设备网和办公网隔离；
- 使用千兆全双工交换机；
- 为录像和证据使用独立 SSD；
- 断网时本地仍能保存事件和视频；
- 关键事件使用 TCP、HTTP 或 WebSocket，UDP 只做状态广播。

## 6. FinishLynx 风格主界面

以用户提供的 FinishLynx 界面截图为主要布局参考：

```text
┌─────────────────────────────────────────────────────┐
│ 菜单、工具栏、赛事状态、设备状态、待判数量             │
├───────────────────┬─────────────────────────────────┤
│ 赛事和设备信息     │ CycleRace 通过记录/判读结果表     │
├───────────────────┼─────────────────────────────────┤
│ 澳亚特线阵图像     │ 普通摄像头 A 或双摄像头画面       │
│ 垂直判读线         │ 播放、暂停、逐帧、慢放            │
├───────────────────┴─────────────────────────────────┤
│ 统一时间线、芯片标记、线阵位置、视频位置               │
├─────────────────────────────────────────────────────┤
│ 上一人 下一人 绑定号码 标记未知 保存证据 建立修正建议   │
└─────────────────────────────────────────────────────┘
```

### 6.1 顶部状态区

显示：

```text
赛事、组别、圈次
CycleRace：已连接/断开
澳亚特：采集中/已停止/待读取
摄像头 A/B：在线/断流/重连中
当前同步误差
待判读数量
```

### 6.2 结果表

建议字段：

```text
通过序号
芯片号码
芯片时间
线阵判读号码
视频判读号码
圈次
状态
证据
```

状态：

```text
已确认、待判读、芯片缺失、号码不清、顺序冲突、未知运动员、修正建议
```

结果表的每一行都是一个可定位的判读对象，不应只把它当成最终成绩表。

### 6.3 图像和视频区

启用澳亚特时：

```text
左侧：线阵总览、放大区域、垂直判读线
右侧：摄像头 A 或双摄对比
```

未启用澳亚特时：

```text
下方区域：摄像头 A + 摄像头 B 双画面
```

设备未连接时隐藏对应区域，不影响其他模式运行。

## 7. 统一时间轴和联动

### 7.1 联动规则

点击结果表中的一条记录：

```text
结果表记录
   ↓
摄像头 A 跳转
   ↓
摄像头 B 跳转
   ↓
澳亚特线阵判读线跳转
```

拖动统一时间线：

```text
摄像头 A、摄像头 B、线阵图像同步移动
```

主要操作：

```text
选择对象 -> 移动判读线 -> 查看视频 -> 输入号码 -> Enter 确认
```

新片段到来时进入待判队列，不强制打断当前对象。“跟随最新”打开时才自动跳到最新片段。

### 7.2 时间数据

必须保存：

```text
CycleRace passage_time_ms
普通视频 source_pts_us
澳亚特 device_tick
VideoPipe monotonic_time
消息接收时间
视频文件和帧号
每台设备的 offset
```

不能把以下内容直接当成拍摄时间：

```text
网络消息到达时间
VideoPipe 对象创建时间
frame_index / FPS 的简单换算
```

第一版允许的体验目标：点击芯片事件后跳到视频前后约 1 秒范围，再由操作员拖动和逐帧确认。正式版本需要源 PTS、统一时钟和现场校准。

## 8. 澳亚特 RGB 适配

已确认的 RGB 基础结构：

```text
48 字节文件头
每条扫描记录 3080 字节
4 字节设备 tick
4 字节状态标志
3072 字节 RGB 像素
1024 个 CCD 像素 × 3 通道
```

已观察到的标志：

```text
0x01000000：拍摄开始
0x02000000：拍摄结束
```

适配器职责：

1. 以只读方式监视 RGB 文件增长。
2. 只解析完整扫描记录，避免读取半条记录。
3. 识别完整的开始和结束片段。
4. 允许短片段、孤立结束标志和文件重置进入异常状态。
5. 为每段保存独立元数据和图像索引。
6. 不覆盖原始 RGB，不依赖 JPG 作为实时接口。

现有解析基础：`scripts/parse_ayt_rgb.py`。

## 9. 现场业务流程

### 9.1 正常通过

```text
CycleRace 收到芯片
        ↓
发送 passage 事件
        ↓
VideoPipe 在统一时间线上增加标记
        ↓
操作员点击记录
        ↓
普通视频和线阵图像跳转
        ↓
人工确认号码和状态
        ↓
保存判读和证据
```

### 9.2 芯片漏读

普通摄像头必须连续录像或使用循环缓冲，不能只在收到芯片后才录像。

```text
线阵发现实际有 4 个通过位置
CycleRace 只有 3 条芯片记录
        ↓
VideoPipe 建立匿名通过槽位
        ↓
普通视频确认号码
        ↓
生成“疑似芯片漏读”建议
        ↓
CycleRace 操作员确认
        ↓
正式成绩由 CycleRace 处理
```

```text
  line_position, video_pts_us, status, operator

  image_path, video_clip_path, source_hash, created_at
```

### 10.2 CycleRace -> VideoPipe

```json
{
  "message_id": "uuid",
  "event_id": "race-stage-1",
  "passage_id": 153,
  "sequence": 38,
  "chip_id": "23",
  "bib": "23",
  "passage_time_ms": 1787217138520,
  "lap": 3

```

必须支持：

- 消息确认；
- 去重；
- 断线重连；
- 历史补发；
- 本地持久化；
- 协议版本。

### 10.3 VideoPipe -> CycleRace

VideoPipe 只发送修正建议：

```text
目标通过序号
疑似号码
判读来源
证据索引
判读原因
操作员和时间
建议状态
```

CycleRace 操作员确认后才进入正式成绩流程。

## 11. 证据和审计

每个判读对象保存：

```text
比赛、组别、圈次
CycleRace 原始事件
视频文件、源 PTS 和帧位置
摄像头 A/B 位置
澳亚特 RGB 文件、片段和扫描位置
截图或视频片段
人工判读结果
修改前后内容
操作员和操作时间
文件哈希
```

原则：

- 原始录像和 RGB 不覆盖；
- 未知运动员也必须保存；
- 修改采用追加记录；
- VideoPipe 重启后恢复事件和待判队列；
- 证据可以离线重新打开和复核。

## 12. 开发计划

### 阶段 0：现场接口确认

目标：确定可实现边界。

任务：

- 确认 CycleRace 可以发送的 passage 字段；
- 确认普通摄像头的 RTSP、源 PTS 和录像能力；
- 确认澳亚特目录共享或 SDK 条件；
- 确认三台电脑的固定 IP 和时间同步；
- 确认现场操作员的拍摄和判读流程。

输出：接口字段表、网络拓扑图、时间校准记录、现场测试清单。

### 阶段 1：CycleRace 事件接口

任务：

- 接收 passage 事件；
- 消息确认、去重和重发；
- 断线重连和历史补发；
- 本地事件持久化；
- 事件版本兼容。

验收：连续接收 1000 条事件无丢失、无重复；重启后可以恢复。

### 阶段 2：单摄像头 MVP

任务：

- RTSP 连续录像或循环缓冲；
- 保存源 PTS；
- 建立视频文件时间索引；
- 点击芯片事件跳到视频附近；
- 播放、暂停、慢放、逐帧和前后拖动。

验收：操作员可以通过一个窗口按芯片时间找到对应视频并保存证据。

### 阶段 3：FinishLynx 风格判读界面

任务：

- 比赛事件窗口；
- 通过结果表；
- 视频判读区；
- 手动号码绑定；
- 未知对象和状态过滤；
- 待判队列；
- 键盘快捷操作。

验收：新事件到来不打断当前判读；待判数量始终可见、可追踪。

### 阶段 4：双摄像头

任务：

- 两路独立采集和录像；
- 两路源 PTS 和独立时间偏移；
- 双画面同步播放；
- 单路断流自动重连；
- 单路放大和双路对比；
- 双路截图和视频片段导出。

验收：同一 passage 可以同时定位两路摄像头，并能显示同步误差。

### 阶段 5：证据和修正建议

任务：

- 截图和视频片段；
- 操作审计；
- 文件哈希；
- VideoPipe 提交修正建议；
- CycleRace 人工确认流程。

验收：每一条建议都能回到原始视频或 RGB 证据。

### 阶段 6：澳亚特线阵接入

任务：

- RGB 增量解析；
- 分段监视和容错；
- 线阵总览、放大和垂直判读线；
- RGB tick 与统一时间轴映射；
- 与普通视频和 CycleRace 联动。

验收：拍摄完成一段后，该段及时进入待判队列；下一段拍摄不覆盖上一段。

### 阶段 7：现场联合验收

必须覆盖：

- 单人、小集团、大集团；
- 芯片漏读、重复读和顺序冲突；
- 号码遮挡；
- 双摄像头断流；
- 澳亚特连续多段拍摄；
- 网络中断；
- VideoPipe 中途重启；
- 长时间比赛运行。

建议使用不少于 30 个真实通过事件记录：

```text
事件丢失率
视频定位误差
双摄同步误差
人工判读耗时
证据保存成功率
断线恢复时间
```

### 阶段 8：可选 AI

仅在基础系统稳定后评估：

- YOLO 目标候选；
- 号码区域候选；
- OCR 候选号码；
- 运动员跟踪；
- 自动生成待确认对象。

AI 只能提供候选，不能替代 CycleRace 官方成绩、人工确认和原始证据。

## 13. 核心验收标准

1. 1000 条 passage 事件无丢失、无重复。
2. 断线恢复后可以补齐事件。
3. 单摄像头点击事件可以定位到目标前后约 1 秒范围。
4. 双摄像头可以独立校准并显示同步偏差。
5. 原始视频、RGB、截图和人工记录全部可追溯。
6. 芯片漏读时仍可以建立匿名通过观察。
7. 澳亚特分段保存后可以立即进入待判队列。
8. 新事件不强制打断当前判读。
9. VideoPipe 不绕过人工确认直接修改正式成绩。

## 14. 风险与暂不解决事项

### 主要风险

- 摄像头源 PTS 不稳定；
- 三台电脑时钟漂移；
- 普通摄像头关键位置被遮挡；
- 澳亚特文件实时共享或 SDK 权限未确认；
- 长时间双路录像造成磁盘和队列压力；
- CycleRace 与 VideoPipe 的接口字段尚未冻结。

### 暂不做

```text
反编译 FinishLynx
复制 FinishLynx 内部代码
依赖 OCR 才能完成判读
依赖 YOLO 才能保存证据
VideoPipe 自动修改正式成绩
只保存 JPG 而不保存原始证据
```

## 15. 最终结论

最终系统确定为：

```text
CycleRace
  官方计时和正式成绩

VideoPipe
  统一判读界面、时间线和证据工作台

普通摄像头
  连续视频和号码确认

双普通摄像头
  两个角度减少遮挡

澳亚特线阵
  精确判断冲线顺序
```

第一版从 **CycleRace + 单普通摄像头 + VideoPipe** 开始；随后增加双摄像头，最后接入澳亚特线阵，形成适合自行车比赛的多源终点判读系统。
